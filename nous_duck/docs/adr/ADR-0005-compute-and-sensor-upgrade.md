# ADR-0005：運算與感測硬體升級

- 狀態：**部分採用**（2026-11-12 使用者決定：雙板＝Pi Zero 2 W＋**Pi 4**、鏡頭沿用 **AR0144** 並**裝在頭上**、麥克風陣列買 **reSpeaker Flex XVF3800 Circular-4** 並**裝在身體上**、加裝實體隱私開關、眼燈改 RGB 用顏色提示鏡頭狀態）；2026-11-13 決定頭上鏡頭旁加**紅外線補光燈**（沒開燈時的備案，ADR-0002 §4.1）；其餘仍為草案
- 日期：2026-11-12
- 相關：[R-001](../requirements/R-001-mobile-companion.md)、[ADR-0002](ADR-0002-indoor-localization-and-navigation.md)、[ADR-0003](ADR-0003-mobile-terminal-wake-and-find.md)、[ADR-0004](ADR-0004-docking-and-charging.md)

## 1. 背景

R-001 要求鴨子能在室內定位導航、帶著麥克風、喇叭與雙目鏡頭到處對話、聽喚醒詞找人、自己回充電座。原版 Open Duck Mini v2 的運算只有 **Raspberry Pi Zero 2 W**（4 核 Cortex-A53 1 GHz、512 MB RAM），上游 BOM 把鏡頭與麥克風標為「not integrated yet」。

鴨子同時要做的事：

| 工作 | 即時性 | 運算量 |
|---|---|---|
| 步態策略（ONNX，50 Hz）＋舵機匯流排 | 硬即時，抖動會影響平衡 | 小 |
| 安全監控（IMU、足底、電壓、溫度、TTL） | 硬即時 | 小 |
| 雙目擷取＋深度＋視覺里程計 | 10～30 Hz | **大** |
| AprilTag 偵測（ADR-0002） | 5～15 Hz | 中 |
| 喚醒詞（sherpa-onnx KWS）＋聲源方向 | 常駐 | 中 |
| 語音雙向串流到 Nous | 即時 | 中（編碼） |
| 人臉偵測與特徵（ADR-0003） | 找人時 | 中 |

Pi Zero 2 W 的 512 MB 記憶體與 A53 核心，不可能同時做到上表全部，而且感測工作一旦搶走 CPU，步態迴圈會抖動。**這是本 ADR 的推論，尚未量測**；P2 階段會做 spike 確認。

## 2. 決定（草案）

### 2.1 運算：採「身體板＋感知板」分離（建議）

| 方案 | 內容 | 優點 | 缺點 |
|---|---|---|---|
| **A. 雙板（建議）** | 保留 Pi Zero 2 W 當**身體板**（上游 runtime 步態＋本機安全）；另加一片**感知板**跑鏡頭、定位導航、喚醒詞、音訊、人臉。兩板以 USB 或 UART 連線 | 步態與上游完全一致；感知當機不會讓鴨子倒下；安全邏輯隔離在最簡單的那一片 | 多一片板子的重量、功耗、空間與線材；兩套系統要維護 |
| B. 單板升級 | 用 Pi 5 等級的板子取代 Pi Zero 2 W，全部工作在同一片，用 CPU 核心隔離保護步態迴圈 | 接線簡單、內部延遲最低 | 機身要改（Pi 5 約 85×56 mm，Zero 約 65×30 mm）；感知負載可能干擾步態，要實測抖動；安全與感知同一個故障域 |
| C. 不升級，全部串流到 Mac mini | Pi Zero 2 W 只擷取、編碼、上傳，定位與喚醒都在 Mac | 鴨子端最輕 | Pi Zero 2 W 同時擷取雙目與編碼仍很吃緊；**Wi-Fi 一斷就失去定位與喚醒**，走廊中斷線只能停住；不符合「安全與移動不依賴網路」 |

**使用者 2026-11-12 決定採 A，感知板用 Raspberry Pi 4。** 以下保留當初的比較與理由。

建議採 **A**。理由：步態是這隻機器人最脆弱的部分，保持與上游一致最省風險；安全要放在最不會當機的地方。感知板的候選（**型號與尺寸都要查證、實測後才定**）：

- Raspberry Pi 5（4 GB 以上）或 CM5＋小型載板：生態完整、可跑 ROS 2，但體積與功耗較大。
- Zero 尺寸的高效能板（例如 RK3566 系列、內建 NPU 的板子）：尺寸接近 Pi Zero，放得進原機身的機會較高，但軟體生態較弱。

#### 2.1.1 Pi 4 當感知板的考量（2026-11-12）

- **優點**：AIOS 的 RPi 終端就是 Pi 4，已有部署與實機紀錄（AIOS `terminals/rpi4/`，2026-11-05），ADR-0003 的終端路線 A（沿用 AIOS 頁面）可以直接借用這些經驗。
- **尺寸**：Pi 4 板子約 85×56 mm，比 Pi Zero 2 W（65×30 mm）大很多；原版機身中段外框約 150×110 mm（`body_middle_top`／`body_middle_bottom` 從 STL 量的外框），裡面還有電池與舵機驅動板，**放不放得下要實際量內部空間**。放不下就要改機身件（改裝件放 `hardware/compute/`）。
- **功耗與散熱**：Pi 4 負載時功耗明顯高於 Pi Zero 2 W，需要 5V 3A 級的供電與散熱，會縮短續航；上游 BOM 的 5V 穩壓器容量要重新確認。數字要實測。
- **運算餘裕**：Pi 4 同時跑雙目解碼（AR0144 輸出 2560×720 MJPG 併排）、視覺里程計、AprilTag、喚醒詞、語音串流與可能的 Chromium，**可能不夠**。P2 先做 spike 量 CPU 與延遲；不夠時的退路：降低影像解析度與幀率、關掉 Chromium 改用原生終端（ADR-0003 路線 B）、或把部分視覺工作移到 Mac。
- 身體板與感知板的連線：建議 USB（Pi 4 當主機）或 UART；內部訊息沿用 duck-link 子集。

### 2.2 感測器

| 感測器 | 用途 | 建議 | 待決 |
|---|---|---|---|
| 雙目鏡頭 | 定位（視覺里程計、AprilTag）、避障深度、找人 | **已決定：Waveshare AR0144 Stereo USB Camera (A)**（沿用 AIOS 的經驗）：雙全域快門、單眼 1280×720、基線 52 mm、水平視角 65°、UVC 免驅動、輸出 2560×720 MJPG 併排（規格引自 AIOS `docs/11`） | 裝頭上還是身上（§2.3）；模組尺寸與重量要量；基線 52 mm 的深度有效距離要實測 |
| 麥克風陣列 | 喚醒詞、對話、**聲源方向（DOA）** | **已決定：reSpeaker Flex XVF3800 Circular-4（USB、不含 XIAO），裝在身體上**（§2.3.1）；與使用者的 FamilyRecorder 專案用的標準版 XVF3800 同晶片，方向讀取可沿用其作法；選型見 [`hardware/sensors/mic_array_selection.md`](../../hardware/sensors/mic_array_selection.md) | Flex 的 USB ID 與控制指令是否與標準版相同，到貨後驗證 |
| 喇叭＋功放 | 說話、叫人起床 | 上游 BOM 已有小喇叭與功放（表情套件）；叫人起床可能需要更大音量，要實測 | 音量是否足夠 |
| IMU | 姿態、跌倒、視覺里程計融合 | 沿用上游 BNO055 | — |
| 紅外線補光燈 | 沒開燈時讓鏡頭看得到 AprilTag、特徵與深度（[ADR-0002 §4.1](ADR-0002-indoor-localization-and-navigation.md#41-沒開燈時的備案紅外線補光2026-11-13-使用者同意以此為主)） | **已決定方向（2026-11-13）**：頭殼上緊貼 AR0144 的 850 nm 紅外線 LED，由 Pi 4 依畫面亮度開關與調光 | AR0144 模組有沒有 IR-cut 濾片；850／940 nm；LED 型號、耗電、發熱、重量、照射距離都要實測 |
| ToF 落差感測器（建議） | 不靠光線偵測前方樓梯口與落差，暗處的禁區雙重保護 | 多區塊 ToF（例如 VL53L5CX 一類），裝在身上朝前下方 | 是否加裝、型號、安裝位置 |
| 電流感測（選配） | 電量估算、回充判斷（ADR-0004） | INA219／INA226 一類 | 是否加裝 |

### 2.3 鏡頭裝在頭上還是身上

| | 頭上 | 身上 |
|---|---|---|
| 找人、看人、對話 | 自然，轉頭就能看 | 要轉整個身體 |
| 定位與避障 | 鏡頭位姿要經 4 個頸頭關節換算，需要讀舵機位置並做時間同步 | 鏡頭與 IMU 固定，最單純 |
| 重量 | 加在頭部，頸部舵機負擔變大，重心變高 | 加在軀幹，對步態影響較小 |

**使用者 2026-11-12 決定鏡頭裝在頭上。** 因此：

- 頭殼 `head.stl` 要重新設計，容納 AR0144 與旁邊的紅外線補光燈（改裝件放 `hardware/sensors/`）。
- 定位要用 4 個頸頭關節（ID 30–33）的回讀角度換算鏡頭位姿，影像與關節讀值要時間同步（ADR-0002 §4）。
- 頭部變重、重心變高：先量 AR0144、麥克風陣列、新頭殼的重量，在模擬中檢查頸部舵機扭力餘裕與步態（§2.4）。頸部撐不住時的退路是把鏡頭也移到身上。

#### 2.3.1 麥克風陣列裝在身體上（2026-11-12 使用者決定）

使用者的理由：裝在身體上才能**固定知道正面方向**。比較如下：

| | 頭上 | 身體上（採用） |
|---|---|---|
| 正面方向 | 也能知道，但要用頸頭 4 顆舵機的回讀角度換算，且收音時刻與關節讀值要同步；頭在轉的時候換算誤差較大 | **麥克風的 0° 永遠是身體正前方**，校準一次就固定；聲源角度直接就是「要往哪邊轉身」 |
| 走去找人 | 先轉頭再轉身，要兩段換算 | 直接依角度轉身，最單純 |
| 頸部負擔 | 加上麥克風板與排線 | 頭部只剩鏡頭，**頸部舵機負擔較小**，也少一組穿過 4 個關節的線 |
| 收音 | 位置高、離舵機稍遠 | 離髖部舵機較近、頭頸可能遮擋一點後方聲音；要實測噪音與方向準確度 |

安裝要點：

- 圓形陣列要**水平**安裝才能判斷水平方向（裝在胸前直立的 `body_front` 上不行）。候選位置是機身頂面靠頸部後方；`body_middle_top` 已經印好，**用外掛支架固定，不重印**，確切位置依 CAD 決定。
- Flex 的處理板放在機身內，以排線接麥克風板。
- 麥克風孔要露在外面，不能被外殼包住。
- 喇叭盡量遠離麥克風，讓回音消除比較好做。
- 走路時身體會晃與轉，聲源方向只在鴨子**停下時**取樣（ADR-0003 §4）。

### 2.4 重量與步態策略

任何加裝（感知板、鏡頭、麥克風、喇叭、充電觸點）都會改變**質量、重心與轉動慣量**。上游步態策略是在原版質量分布下訓練的，可能不再穩定。因此：

1. 先在 `nous_duck/sim/` 複製一份上游 MJCF，加入新元件的質量與位置（不改上游檔）。
2. 用原策略在模擬中測試；不穩定就用上游訓練流程（Open_Duck_Playground）重新訓練。
3. 實機驗證後才算通過。這是 P2 的 gate。

## 3. 後果

- 機身需要改裝空間（感知板、鏡頭、麥克風、線材），改裝件放 `nous_duck/hardware/`，不改上游 STL。
- 尚未列印的 15 件裡：`body_back` 確定要改（背後充電觸點，ADR-0004）；`head` 確定要改（AR0144）；`body_middle_bottom`、`battery_pack_lid` 可能要為 Pi 4 的安裝與散熱改。**這 4 件先暫緩列印**，等量完內部空間再決定。
- 電池續航會下降，要實測；可能需要更大容量的電池。
- 身體板與感知板之間的內部協定：建議沿用 duck-link 的 command／state／event 子集（意圖＋速度指令），讓身體板的 safety 仍是最後一道關卡。
