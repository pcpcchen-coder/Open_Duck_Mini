# ADR-0016：導航核心的作法，以及模擬對既有 ADR 的回饋

- 狀態：**草案（Proposed）**。依據只有模擬與單元測試（[驗證紀錄](../validation/sim-nav-2026-11-25.md)），沒有實機
- 日期：2026-11-26
- 相關：[ADR-0002](ADR-0002-indoor-localization-and-navigation.md)（定位與導航）、[ADR-0004](ADR-0004-docking-and-charging.md)（回充）、[ADR-0009](ADR-0009-duck-link-transport-and-command-bridge.md)（指令橋接與 safety）、[ADR-0011](ADR-0011-gesture-library.md)（動作庫）、[`robot/navigation/`](../../robot/navigation/README.md)、[`sim/`](../../sim/README.md)

## 1. 背景

ADR-0002 §5.4 把「ROS 2 或自寫最小版」留到 spike 之後決定；ADR-0009 §2.5 的 safety 數值、ADR-0004 的回充流程都寫明要等模擬與實機量測。2026-11-25 夜間，鏡頭、足底開關、充電座都還沒裝，實機不能走，所以先在 MuJoCo 裡把走路、導航、回充做出來。這份 ADR 記下當時的選擇，以及模擬結果跟既有 ADR 的假設不一樣的地方。

## 2. 決定（草案）

### 2.1 第一階段用自寫的最小 Python 導航核心

`robot/navigation/duck_nav`：只依賴 numpy，不依賴 MuJoCo、鏡頭驅動或舵機。對外只有 `SensorFrame`（進）與 `NavOutput`（出）兩個型別，每個控制週期呼叫一次 `Navigator.step()`。

- 理由：能在沒有硬體的情況下先把行為與安全規則用測試固定下來；同一份程式在模擬與實機上跑，只換填 `SensorFrame` 的那一層。
- 不是否定 ROS 2：ADR-0002 §5.4 的比較（CPU、記憶體、延遲）還沒做。之後若換成 Nav2，`SensorFrame`／`NavOutput` 這層介面與測試情境可以留著當驗收。

### 2.2 導航只用步態反應表裡可靠的指令

模擬量到上游策略有起步門檻（§3.1），所以導航的速度指令固定為：前進 0.15、後退 −0.15、原地轉 ±1.0／±0.6，轉向連續可調，**不用側移**。「指令 → 實際機身速度」做成一張查表（`gait_response.*.json`），定位的短程里程也用它。實機能走之後用同樣的方法重量一張，換檔案即可。

### 2.3 定位：標籤為主，里程只補空檔

照 ADR-0002：EKF 融合 AprilTag 觀測與短程里程，不用步數。短程里程目前是「實際送出的指令 → 步態反應表」＋陀螺儀偏航，是視覺慣性里程的替身，所以過程雜訊給得大。兩個門檻：不確定度偏高時先停下轉頭看；超過「未定位」門檻就不再前進，只原地轉身找標籤。

### 2.4 回充：對位線預先偏移，轉身後盲退

照 ADR-0004 §2.2（面向充電座對位 → 轉身 180° → 倒退）。模擬裡多做了三件事：

1. 轉身前不是站在正中線，而是預先偏掉「轉身會造成的位移」與「倒退時的固定側滑」。
2. 倒退時轉向很弱，而且一轉向機身會先往同一側滑，所以只做小幅航向修正，靠近導引座就只維持航向。
3. 留一個橫向校正量（`dock_lateral_trim_m`），由實際量到的平均偏差決定。

沒收到充電訊號就退出重來，最多 3 次。「開始充電」只認電氣訊號；沒有訊號來源時任務回報 `dock_failed`，不宣稱已充電。

### 2.5 被抱起來要由身體端告訴導航

`SensorFrame.lifted`（對應 duck-link 已有的 `picked_up` 事件）。收到就丟掉定位、重新找標籤。沒有這個訊號時，鴨子會照舊的估計繼續走到標籤對不上為止，這不可接受。

## 3. 模擬對既有 ADR 的回饋

都是**模擬值**，要實機確認後才能改那些 ADR；先記在這裡。

### 3.1 對 ADR-0009 §2.5（safety 初始值）

| ADR-0009 的假設或初始值 | 模擬結果 | 建議 |
|---|---|---|
| 室內上限 vx 0.10、vy 0.10、yaw 0.6 | 從站立起步需要前進 ≥ 0.10、後退 ≤ −0.12；vy 只有 +0.20 會起步；yaw −0.3 不起步、±0.6 以上可靠。指令 0.15 的實際速度約 0.115 m/s | 上限若設在 0.10，前進剛好卡在門檻、後退完全走不動。實機量過之前，上限先維持上游範圍（vx ±0.15、yaw ±1.0），用「實際速度」而不是「指令值」來談快慢 |
| 「速度為 0 時策略仍會原地踏步」，所以要等兩腳著地 0.3 s 才暫停 | 速度為 0 時不踏步，兩腳一直著地；指令歸零後 0.5～0.7 s 內兩腳著地並持續 0.3 s，滑行 2～4 cm | 規則本身可以留著（它在兩種情況下都安全），但「逾時 2 s」的說明要改；實機要確認是否真的不踏步 |
| 加速度限制 vx 0.01 m/s、yaw 0.05 rad/s 每圈 | 有沒有限制都穩定；有限制時起步慢約 0.2 s | 維持 |
| 頭部依上游範圍夾限 | 走路時 head_yaw ≥ 0.8 或 ≤ −0.5、head_pitch 大角度、neck_pitch ≥ 0.3 會讓步態停下；neck_pitch ≥ 0.9、head_yaw ≤ −1.0 會跌倒（站著也會） | 走路時頭部範圍要比站著時小很多；實機驗證前先用保守值（走路時 head_yaw ±0.3、其餘 0） |
| `walk` 的 `duration_s` 上限 3 s | 起步到 90% 速度要 1.5～1.9 s | 3 s 的 `walk` 大約只有一半時間在穩態，Nous 端估距離時要知道 |

### 3.2 對 ADR-0011（動作庫）

具名動作若在走路時做頭部動作，要先過 §3.1 的頭部限制；站著時 neck_pitch 大角度同樣要避開。

### 3.3 對 ADR-0004（回充）

- 轉身 180° 的位移 7～12 cm、倒退時每退 1 m 側滑約 0.1～0.2 m（模擬），都比 V 形座的捕捉範圍 ±34 mm 大，所以一定要預先補償或校正。
- 補償後第一次進導引座的橫向偏差標準差約 17 mm，60 趟裡 50 趟第一次就在捕捉範圍內。盲退的精度大致就到這裡。
- 想再提高：加大 V 形座的捕捉寬度；或在充電座對面加一張近距離的標籤，讓倒退時鏡頭有東西可看；或加朝後的感測器。這些是硬體決定，列為待決。

### 3.4 對 ADR-0002

- 里程不可靠有數字了：指令積分走約 4 m 終點差 0.19～0.53 m，條件一變誤差就換樣子。
- 走廊這種只有側牆的地方，貼在側牆的標籤斜角太大讀不到（mock 與真的偵測器的斜角極限不同，但方向一致）。**標籤要貼在走道盡頭的牆上**，沿著走的方向才看得到。
- 門關著時從上一個房間的門口就看得到門板，所以「走到門前再回報」要另外做（已做）。

## 4. 後果

- `robot/navigation/` 有了可以測試的核心；`sim/` 有全身走路與導航的模擬。
- A 線的 duckd 要提供 `applied_cmd`、`gyro_z`、`stepping`、`lifted`、`fallen`、`charging`，並把 `NavOutput` 當成 `control_source: mission` 的指令來源。
- 協定要補的東西另寫提案（[`protocol/proposals/c-nav-mission-events.md`](../../protocol/proposals/c-nav-mission-events.md)），這裡沒有動 schema。

## 5. 待決

1. §3.1 的每一項都要實機量測後才能修訂 ADR-0009。
2. ROS 2／Nav2 與自寫版的比較（ADR-0002 §5.4）。
3. 回充要不要加硬體輔助（§3.3）。
4. 步態反應表與回充校正量在實機上怎麼量、多久重量一次（電池電壓、地板材質都會影響）。
