# BNO055 的 I2C 讀值錯誤：改用 i2c-gpio（2026-11-28）

- 分支：`claude/duck-posture-duckd`（PR #67）
- **驗證層級：實機（Pi 4＋BNO055），唯讀量測**。只讀暫存器（寫的只有暫存器位址），沒有改 IMU 的模式或校正；BNO055 這時在開機預設的設定模式（沒有融合輸出），所以**姿態資料本身沒有驗證**。
- 使用者要求「I2C 調慢：讓 IMU 讀值穩定」，知道要重開 Pi；這次重開了 3 次（21:00、21:02、21:04 左右），每次重開後 duckd、duck-console、duck-voice、duck-terminal、duck-settings 都自動回來（`active`），`throttled=0x0`。
- 量測腳本：[`robot/deploy/pi4/bno055_i2c_probe.py`](../../robot/deploy/pi4/bno055_i2c_probe.py)

## 1. 方法

在 `/dev/i2c-1` 對 0x28 重複讀 5 個值固定不變的暫存器，每輪各讀 1 次：

| 暫存器 | 正確值 |
|---|---|
| 0x00 晶片 ID | 0xA0（160） |
| 0x3B UNIT_SEL | 0x80（128） |
| 0x41 AXIS_MAP_CONFIG | 0x24（36，出廠預設） |
| 0x34 溫度 | 36°C 上下 |
| 0x07 頁碼 | 0 |

另外讀 500 次 8 位元組的四元數（0x20），量每次讀取的時間。

## 2. 結果

| I2C 設定 | 輪數 | 晶片 ID 錯 | UNIT_SEL 錯 | AXIS_MAP 錯 | 溫度錯 | 頁碼錯 | 1 位元組讀取 | 四元數讀取 |
|---|---|---|---|---|---|---|---|---|
| 硬體 I2C 100 kHz（原本） | 2000 | 3（讀成 0xD0） | 6（0xC0） | 1559（0xA4、0x92） | 1576（164、146） | 1598（128） | 0.66 ms | 1.68 ms |
| 硬體 I2C 50 kHz | 2000 | 0 | 0 | 24 | 31 | 31 | 1.14 ms | 2.88 ms |
| 硬體 I2C 10 kHz | 2000 | 0 | 0 | 22 | 20 | 21 | 4.60 ms | 11.49 ms |
| **i2c-gpio（軟體 I2C）** | 2000＋10000 | 0 | 0 | 0 | 0 | 0 | 0.36～0.38 ms | 0.91～0.95 ms |

- 硬體 I2C 的錯幾乎都是**第 7 位元被設成 1**（36→164、0→128、0x24→0xA4），少數是整個位元組右移一位再補 1（0xA0→0xD0、0x80→0xC0）。這是 BNO055 clock stretching 時 Pi 硬體 I2C 的已知問題。
- 降速有改善，但 10 kHz 還是約 1%，而且讀一次四元數要 11.5 ms。四元數的最高位元錯一次，正負號就反了，對跌倒判斷不能接受。
- i2c-gpio：**12000 輪、60000 次讀取 0 錯**，讀取還比硬體 I2C 100 kHz 快。上游 runtime 用的 Blinka `busio.I2C(board.SCL, board.SDA)` 掃描得到 `0x28`。

## 3. 改了什麼

Pi 的 `/boot/firmware/config.txt`（備份在 `config.txt.bak-20261128-i2c`）：

```
#dtparam=i2c_arm=on  # 2026-11-28 改用 i2c-gpio（見下）
# 2026-11-28 Nous Duck：……改用 i2c-gpio，一樣是 /dev/i2c-1、GPIO2/3
dtoverlay=i2c-gpio,bus=1,i2c_gpio_sda=2,i2c_gpio_scl=3,i2c_gpio_delay_us=2
```

repo：[`setup_runtime.sh`](../../robot/deploy/pi4/setup_runtime.sh) 的 I2C 那一步改成設定 i2c-gpio（關掉 `dtparam=i2c_arm=on`、移除 `i2c_arm_baudrate`、加上 overlay，改之前先備份），不再用 `raspi-config do_i2c`。腳本只做過 `bash -n` 語法檢查，**沒有在新的 SD 卡上跑過**。

## 4. 限制與下一步

- i2c-gpio 是軟體一位元一位元送，傳輸時會占 CPU；上游 50 Hz 讀四元數約占 1 顆核心的 5%（0.95 ms × 50），沒有量實際負載。
- §1～§3 量測時 IMU 在設定模式，沒有融合輸出。校正與姿態讀值見 §5；前後、左右兩軸的方向還沒用傾斜測試確認。
- duckd 還沒有讀 IMU，跌倒判斷還沒做（ADR-0020 §2.2）。

## 5. 校正（21:10～21:12，使用者要求「好，校正 IMU」）

用上游 runtime `376de65` 的 `scripts/calibrate_imu.py`（`raw_imu.Imu(50, calibrate=True, upside_down=False)`：NDOF 模式，等系統、陀螺儀、加速度計、磁力計四項都到 3，存 `imu_calib_data.pkl`）。在 Pi 的 `~/duck/Open_Duck_Mini_Runtime/scripts/` 執行，所以檔案存在那裡，也就是上游走路程式（工作目錄 `scripts/`）會讀的位置。使用者照指示把鴨子轉 6 個方向、在空中畫 8 字、放回桌上。這段期間舵機沒有動過。

| 時間（開始後） | (系統, 陀螺儀, 加速度計, 磁力計) |
|---|---|
| 2 秒 | (0, 3, 0, 0) |
| 55 秒 | (0, 3, 1, 0) |
| 92～94 秒 | 磁力計 1 → 2，系統 3 |
| 105 秒 | 磁力計 3 |
| 107 秒 | **(3, 3, 3, 3)**，存檔 |

偏移量：加速度計 (−75, −40, −112)、陀螺儀 (−1, −4, 1)、磁力計 (−364, −726, 54)。`imu_calib_data.pkl` 128 bytes，只在 Pi 上，沒有進 repo。

校正後用上游走路程式用的 `mini_bdx_runtime.imu.Imu(50, upside_down=False)`（IMUPLUS 模式、載入上面的偏移量）讀 3 秒，鴨子站在桌上：

- 尤拉角 (x, y, z) ＝ (−0.7°, −1.9°, 0.0°)，6 次讀值都一樣；重力 (0.31, −0.11, 9.80) m/s²。
- 校正狀態 (0, 3, 3, 0)：IMUPLUS 模式不用磁力計，系統與磁力計是 0 是正常的；陀螺儀、加速度計 3。
- 溫度 35°C（之前讀錯會變成 163）。

站立時接近水平，和模擬的站姿（機身俯仰約 −0.4°～−1.1°）差不多。**前後、左右兩軸的正負方向還沒確認**：要使用者讓鴨子往前低頭、往右傾各一次，看哪一個軸、往哪個方向變。

- BNO055 不會自己記住校正值，每次開機由程式載入 `imu_calib_data.pkl`。
- 加速度計偏移量會隨溫度和裝機狀況漂移，多久要重校還不知道。
