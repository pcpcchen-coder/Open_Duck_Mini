- 分支：`claude/tender-bohr-mz85k5`
- 對象：[`nous_duck/robot/deploy/pi4/flash_sd_macos.sh`](../../robot/deploy/pi4/flash_sd_macos.sh)、[`check_pi4.sh`](../../robot/deploy/pi4/check_pi4.sh)
- **驗證層級：雲端容器靜態檢查**（Linux，非 macOS）。**未在 Mac 上實際燒錄、未在 Pi 4 上開機。**

## 1. 映像本身

| 項目 | 結果 |
|---|---|
| 映像 | `2026-10-06-raspios-trixie-arm64-lite.img.xz`（Raspberry Pi OS Lite 64-bit，Imager 清單標示支援 `pi4-64bit`） |
| SHA-256 | `483db18a48da399b5b7022ffae9a07bc6d99daab30e593aedac09b69ff422843`，與官方 `.sha256` 一致 |
| Imager 清單的 `init_format` | `cloudinit-rpi` |
| 開機分割區（FAT，起始 LBA 16384，512 MiB） | 有預設的 `user-data`、`network-config`、`meta-data`（全是註解） |
| `/etc/cloud/cloud.cfg.d/99_raspberry-pi.cfg` | `datasource_list: [NoCloud, None]`，`seedfrom: file:///boot/firmware` |
| cloud-init 版本 | 25.2；network renderer `netplan` → NetworkManager |
| SSH | 預設沒啟用；`sshswitch.service` 看到 `/boot/firmware/ssh` 才啟用 → 腳本會 `touch ssh`，runcmd 也會 `systemctl enable --now ssh` |
| NoCloud 的 meta-data key | 原始碼用 `instance-id`（連字號）；映像預設檔寫的 `instance_id` 不會被讀到 → 腳本用 `instance-id` |

讀法：用 Python 解析 MBR 分割表，`dd` 切出兩個分割區，FAT 用 `pyfatfs` 讀、ext4 用 `debugfs` 讀。

## 2. 產生的設定檔

用 `--render-only` 產生兩組：一般值，以及含中文、空白、雙引號、反斜線、`#`、`:` 的刁鑽 SSID／密碼（測 YAML 跳脫）。

| 檢查 | 工具 | 結果 |
|---|---|---|
| `user-data` schema（strict） | 映像內附 cloud-init 25.2 的 `validate_cloudconfig_schema` | 通過 |
| `meta-data` | YAML 解析，確認有 `instance-id` | 通過 |
| `network-config`（v2，含 `wifis`） | `netplan generate --root-dir`（netplan 1.1.2）。cloud-init 自己的 v2 schema 不含 `wifis`，在 Pi 上它也是交給 netplan 驗證 | 通過；產生 `netplan-wlan0-<SSID>.nmconnection`（`key-mgmt=wpa-psk`、`pmf=2`）、`netplan-eth0.nmconnection`、`netplan-regdom.service` |
| 刁鑽字元 | YAML 解析回來的 SSID／密碼與輸入逐字相同 | 通過 |
| 腳本語法 | `bash -n` | 通過 |

## 3. 補充：cloud-init 快取裡的明文副本（同日修正）

使用者已把燒好的卡插上 Pi 4 之後，重新讀了 cloud-init 25.2 原始碼（`git clone --branch 25.2 https://github.com/canonical/cloud-init`）：

| 檔案（`/var/lib/cloud/instances/<id>/`） | 內容 | 來源 | 第一版 runcmd 有沒有刪 |
|---|---|---|---|
| `user-data.txt`、`user-data.txt.i` | 原始 user-data（含 `plain_text_passwd`） | `cloudinit/helpers.py` 的 `userdata_raw`／`userdata` | 有 |
| `obj.pkl` | datasource 物件（含原始 user-data） | `obj_pkl` | 有 |
| `cloud-config.txt` | 合併後的 cloud-config（含 `plain_text_passwd`），mode 600 | `cloudinit/handlers/cloud_config.py` `_write_cloud_config` | **沒有** |
| `network-config.json` | 網路設定（含 Wi-Fi 密碼），mode 600 | `cloudinit/stages.py` `_write_network_config_json` | **沒有** |

兩個漏掉的檔案都只有 root 讀得到，但仍違反「首次開機後清掉明文」的設計。修正：

- `flash_sd_macos.sh` 的 runcmd 改成逐一清掉每個 `instances/*/` 底下的上述檔案（含 `vendor-cloud-config.txt`、`vendor2-cloud-config.txt`）。
- 確認不會被寫回：`obj.pkl` 只在 `activate_datasource`（init 階段）寫入，runcmd 在 final 階段執行，之後 cloud-init 又被停用。
- `/run/cloud-init/` 的 `instance-data-sensitive.json`、`combined-cloud-config.json` 也有明文，但在記憶體檔案系統上，重開機就消失。
- Wi-Fi 密碼仍留在 `/etc/netplan/50-cloud-init.yaml`（600 root），這是開機連線需要的。
- **已經用第一版腳本燒好、開過機的卡**：用 `check_pi4.sh --clean` 清掉，不必重燒。

修正後的 `user-data` 重新用 cloud-init 25.2 strict schema 檢查：通過。

## 4. 開機後檢查腳本 `check_pi4.sh`

[`check_pi4.sh`](../../robot/deploy/pi4/check_pi4.sh) 在 Mac 上透過 SSH 檢查 Pi（32 項，其中 5 項只列資訊），輸出 Markdown 報告。雲端容器裡做過的測試：

| 測試 | 方法 | 結果 |
|---|---|---|
| 語法 | `bash -n`、`shellcheck -S warning` | 通過 |
| 遇到缺少的指令不中斷 | 在雲端容器（Ubuntu、沒有 `vcgencmd`、`nmcli`、systemd）直接跑遠端檢查部分 | 跑完 32 項，缺少的項目回報「注意」或「失敗」，沒有中斷 |
| 抓得到明文殘留 | 在容器建立假的 `/var/lib/cloud/instances/<id>/`（`cloud-config.txt`、`network-config.json`、`user-data.txt*`、`obj.pkl`） | 「cloud-init 快取明文」失敗，列出 5 個檔名，不印內容 |
| 修正後的 runcmd 清理迴圈 | 從產生的 `user-data` 取出迴圈執行 | 只剩 `boot-finished`、`sem/` |
| `--clean` | 同上的假檔案 | 清掉後重新檢查，「cloud-init 快取明文」通過 |
| 整體流程 | 用假的 `ssh`（在本機執行指令）跑 `bash check_pi4.sh` 與 `--clean` | 報告存到 `~/Downloads/nous-duck-pi4/`，參數引號正確 |
| 連不上時的提示 | 不存在的主機 | 印出 ssh 錯誤與排查建議，exit 1 |

沒測到的：真正的 SSH 連線、macOS 的 bash 3.2 與 `pbcopy`、Pi 上各項指令的實際輸出格式。

## 5. 限制（待實機驗證）

- macOS 部分（`diskutil`、`sudo dd of=/dev/rdiskN`、自動掛載 `bootfs`、bash 3.2 相容性）**沒有執行過**。
- Pi 4 首次開機：Wi-Fi 是否連上、`duck-pi4.local` 是否可解析、apt 安裝、清除明文密碼與停用 cloud-init，**都還沒實測**。
- 只設定 WPA2-PSK；純 WPA3（SAE）路由器可能連不上。
- 實機結果用 `check_pi4.sh` 收集後，另寫一份 `pi4-firstboot-<日期>.md`。
