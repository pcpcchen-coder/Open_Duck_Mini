# Protocol proposal (line B): the scope of validity of `event_id`

Status: **proposal**; the schema has not been changed. Date: 2026-11-26. Proposed by: line B (Nous side, `nous_adapter/`).

## 1. What happened

Real-robot test on the evening of 2026-11-26 (reported by line A): after duckd on the Pi was restarted, the hub on the Mac treated its newly sent events as duplicates and dropped them — `duplicateEvents` accumulated to 11, and none of the `tracking_*` events after the restart were visible in `duckctl events`.

The cause is that the two ends understand `event_id` differently, and the v0 schema does not state its scope of validity:

| | Approach |
|---|---|
| Duck side (duckd) | `event_id` is an in-process serial number: `e_000001`, `e_000002`…, **numbering starts over when the process restarts** |
| Nous side (hub, before the fix) | The dedupe table keeps the most recent 256 `event_id`s across connections; anything already seen is dropped |

Each side on its own conforms to the schema. Put together, the first few events after a duckd restart are bound to collide.

## 2. How it is handled now (fixed; no protocol change needed)

The hub was changed to **clear the dedupe table every time the duck completes `hello` (a new connection)**: deduplication is only valid within the same connection. `nous_adapter/tests/hub.test.ts` has a test that reproduces this situation (numbering the way duckd does, starting again from `e_000001` after a restart).

The cost of this approach: if the duck side, "in the same process, after a disconnect and reconnect", resends events from before the disconnect, the hub will forward them a second time. v0 does not specify whether the duck should resend; duckd currently does not resend, so there is no practical impact at present.

## 3. Recommendation (for a later version)

Choose one of two, and write it into the schema's description:

1. **Specify that `event_id` is unique only within one connection** (which is the current behaviour). The duck does not guarantee no repeats across connections, and Nous does not dedupe across connections. Simplest; no field needs to be added.
2. **Add a `boot_id` to `hello`** (a random string generated each time the duck-side process starts). Nous dedupes by "`boot_id` + `event_id`": when the same process reconnects, resends can still be blocked, and on a restart it is naturally a new scope. If "backfilling events from the disconnected period" is to be done later, this will be needed.

Line B's view: adopt 1 first; add `boot_id` when event backfill really has to be done (for example, mission-completed events must not be lost because of a disconnect).

## 4. Places of the same kind

- `request_id` is generated by Nous (random). If the duck side's "a repeated `request_id` returns the original ack" table is not kept across processes, there is no problem; keeping it across connections is also no problem.
- `mission_id` is generated by the duck; if duckd also uses a serial number, it will repeat after a restart. The Nous side currently uses it only during the lifetime of a single mission and does no matching across restarts, so there is no practical impact, but it should be written down together when the scope is specified.
