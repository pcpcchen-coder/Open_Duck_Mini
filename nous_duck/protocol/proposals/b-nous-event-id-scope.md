# 協定提案（B 線）：`event_id` 的有效範圍

狀態：**提案**，沒有改 schema。日期：2026-11-26。提出者：B 線（Nous 端，`nous_adapter/`）。

## 1. 發生了什麼

2026-11-26 傍晚的實機測試（A 線回報）：Pi 上的 duckd 重啟之後，Mac 的 hub 把它新送的事件當成重複丟掉——`duplicateEvents` 累到 11，重啟之後的 `tracking_*` 事件在 `duckctl events` 都看不到。

原因是兩端對 `event_id` 的理解不一樣，而 v0 的 schema 沒有說它的有效範圍：

| | 作法 |
|---|---|
| 鴨子端（duckd） | `event_id` 是行程內的流水號：`e_000001`、`e_000002`…，**行程重啟就從頭編** |
| Nous 端（hub，修正前） | 去重表跨連線保留最近 256 個 `event_id`；看過的就丟 |

兩邊各自都合 schema。合在一起，duckd 重啟後的前幾則事件一定撞號。

## 2. 現在怎麼處理（已修正，不需要改協定）

hub 改成**每次鴨子完成 `hello`（新連線）就清空去重表**：去重只在同一條連線內有效。`nous_adapter/tests/hub.test.ts` 有重現這個情況的測試（照 duckd 的編法、重啟後從 `e_000001` 再來一次）。

這個作法的代價：如果鴨子端在「同一個行程、斷線重連之後」把斷線前的事件重送一次，hub 會轉發第二次。v0 沒有規定鴨子要不要重送；duckd 目前不重送，所以現在沒有實際影響。

## 3. 建議（給之後的版本）

二選一，寫進 schema 的說明：

1. **規定 `event_id` 只在一條連線內唯一**（就是現在的行為）。鴨子不保證跨連線不重複，Nous 不跨連線去重。最簡單，不用加欄位。
2. **在 `hello` 加一個 `boot_id`**（鴨子端行程每次啟動產生一個隨機字串）。Nous 以「`boot_id`＋`event_id`」去重：同一個行程重連時還能擋掉重送，重啟時自然是新的範圍。之後如果要做「斷線期間的事件補送」，會需要這個。

B 線的看法：先採 1；等到真的要做事件補送（例如任務完成的事件不能因為斷線而遺失）再加 `boot_id`。

## 4. 同一類的地方

- `request_id` 由 Nous 產生（隨機），鴨子端「重複的 `request_id` 回原本的 ack」的表如果跨行程不保留，沒有問題；跨連線保留也沒有問題。
- `mission_id` 由鴨子產生；duckd 若也是流水號，重啟後會重複。Nous 端目前只在一通任務的存活期間用它，沒有跨重啟的比對，所以沒有實際影響，但規定範圍時應該一併寫。
