# 語音路徑：Nous 的聲音怎麼到鴨子、鴨子怎麼聽

狀態：**設計（沒有試聽；路線 A 的終端只做了「不連 Nous、不出聲」的準備與量測）**。日期：2026-11-25；2026-11-26 依修訂後的 ADR-0003、ADR-0005、ADR-0010 更新（見 §7）。

這份文件把 AIOS 的現況（事實）與鴨子現在的硬體對起來，回答四個問題：現在最短可行的對話路徑、麥克風陣列到貨後怎麼變、哪些要 AIOS 改、哪些能在鴨子端做。

- **事實**：從 AIOS commit `c85307861f7562803fb3776407493da49cdc8a83` 的程式碼唯讀查到的，附 `檔案:行號`（相對於 `prototype/ambient-shell/`）。完整清單在 [`aios-integration-plan.md` §2](aios-integration-plan.md#2-查到的事實影響設計的部分)。
- **建議**：本文件的判斷，一律標「建議」。
- **未驗證**：沒有實際跑過或量過的事，一律標「未驗證」。這份文件裡沒有任何一項經過試聽——夜間規則不讓喇叭出聲。

相關決策：[ADR-0003](../../docs/adr/ADR-0003-mobile-terminal-wake-and-find.md)（路線 A／B）、[ADR-0010](../../docs/adr/ADR-0010-duck-voice.md)（語音鏈、變聲、本機音效）。

## 1. 決定設計的五個事實

| # | 事實 | 出處 |
|---|---|---|
| 1 | 兩條即時語音路徑都是**瀏覽器頁面直接用 WebRTC 連雲端模型**：麥克風在頁面取得，助理的聲音是頁面收到的遠端音軌。核心只代轉 SDP，有時另握一條控制用的 WebSocket | `src/realtime.ts`、`src/live-voice.ts`、`server/realtime.ts:558`、`server/live-route.ts:31` |
| 2 | 助理的聲音**只在開始這通對話的頁面**播放（`new Audio()`＋`srcObject`） | `src/main.ts:815-846` |
| 3 | 核心**從不處理原始音訊**，也沒有任何把助理語音送到非瀏覽器裝置的路徑（沒有 PCM／RTP 轉送、沒有 TTS 存檔） | 全 `server/` 搜尋；唯一的例外是 voice-relay 在 Mac 上呼叫 `say` |
| 4 | 輸出裝置用瀏覽器的 `setSinkId` 選；偏好是**全域一份**，不分終端 | `src/audio-devices.ts:105-125`、`server/app.ts:326` |
| 5 | 喚醒詞在頁面裡跑（sherpa-onnx wasm），每個頁面用自己的麥克風；關鍵詞是「Hello Nous」「Hey Nous」 | `shared/wake-runtime.json`、`src/audio/` |

補充一點：ADR-0010 §1 寫「即時語音由 Mac 核心接雲端即時語音模型」。依事實 1，接雲端模型的是**頁面**，核心不經手音訊。這不影響 ADR-0010 的決定（變聲放在 Pi 的系統音訊層），反而是它的理由：聲音只會出現在播放的那台機器上，要改聲音只能在那裡改。

直接的後果：**要讓 Nous 的聲音從鴨子的喇叭出來，而且不在 AIOS 新增音訊管線，唯一的作法是讓「擁有這通對話的頁面」跑在鴨子的 Pi 4 上**——也就是 ADR-0003 的路線 A。路線 B（原生終端程式）需要 AIOS 核心新增整套音訊收送，現在一行都沒有。

## 2. 現在（鴨子只有 USB 喇叭、沒有麥克風）

鴨子聽不到。對話只能在有麥克風的地方發生。三種作法：

### 2.1 作法 0：在 Mac 對話，鴨子做動作（建議先做這個）

```text
人 ──說話──► Mac 的麥克風 ──► Mac 上的 Nous 頁面 ⇄ 雲端模型
                                   │ 聲音：Mac 的喇叭
                                   │ 工具呼叫：app.duck.look／gesture／…
                                   ▼
                    Nous 核心 ── duck-link ──► 鴨子（頭部動作、之後的眼睛）
                    presence（聽／想／說）──────► 鴨子跟著做動作
```

- 聲音從 **Mac** 出來，不是鴨子。要誠實說：這時候是「Nous 在說話、鴨子在旁邊跟著動」，不是「鴨子在說話」。
- 需要 AIOS 的批次 D1（`/duck-link`）、D2（`duck` adapter）、D4a（`presence` 的粗略來源）。**不需要任何新硬體。**
- 本 repo 這一端已經完成並對 mock 鴨子測過：hub、DuckAdapter、PresenceDriver（[`../README.md`](../README.md)）。
- 鴨子端的本機音效（ADR-0010 §6）可以先做，不依賴 Nous。

### 2.2 作法 1：把 Mac 的聲音轉送到鴨子的喇叭（未驗證，不建議當主路線）

想法：讓鴨子的 Pi 變成 Mac 看得到的一個音訊輸出裝置，Mac 上的 Nous 頁面用現有的「選擇聲音輸出裝置」選它。這樣不用改 AIOS，麥克風仍然是 Mac 的。

- 可能的技術：AirPlay 接收端、藍牙喇叭模式、網路音訊（PipeWire／PulseAudio 的網路 sink）。**都沒有試過**。
- 要驗證的事：
  - Chromium 的 `setSinkId` 列不列得出那個裝置（事實 4 只說明它用瀏覽器的裝置清單，沒有說網路裝置會出現）。
  - 延遲。對話用的聲音晚到會讓人以為沒反應，也會讓 Mac 麥克風的回音消除失效（聲音從另一個房間的鴨子出來，Mac 的麥克風可能收得到）。AirPlay 這類協定通常有刻意的緩衝；實際數字**沒有量**。
  - AIOS 的 rpi4 文件寫 Pi 的藍牙「尚未支援」（`terminals/rpi4/README.en.md:217`），指的是 Pi 當終端時接藍牙裝置，不是這個用法，但表示這一塊沒有人驗證過。
- 人要對著 Mac 說話、聲音卻從鴨子出來，鴨子不在 Mac 旁邊時就不成立。
- 結論（建議）：只值得當「麥克風到貨前想先聽聽鴨子的聲音」的實驗，不投入成主路線。

### 2.3 作法 2：先在鴨子上接一支現成的 USB 麥克風，直接走路線 A（建議的最短「鴨子說話」路徑）

AIOS 的 rpi4 終端就是「Pi 4＋USB 麥克風＋喇叭＋Chromium」。鴨子的 Pi 4 接上任何一支 USB 麥克風（例如 rpi4 終端用的那一支），就滿足同樣的條件：

```text
人 ──說話──► 鴨子上的 USB 麥克風 ──► 鴨子 Pi 4 的 Chromium（Nous 頁面，?terminal=<鴨子 ID>）⇄ 雲端模型
                                          │ 聲音：Pi 的音訊輸出 → duck_voice（變聲）→ USB 喇叭
                                          │ HTTP／SSE 經 SSH 通道 → Mac 的 Nous 核心（工具、記憶、設定）
```

- **AIOS 可以完全不改**：終端 ID 只是網址參數（規則 `/^[a-z0-9][a-z0-9-]{0,31}$/`，`shared/terminal.ts:12`）。
- 要做的在鴨子這邊：一份給鴨子用的終端套件（參考 `terminals/rpi4/`：通道、kiosk、開機啟動），差別是鴨子沒有螢幕、終端 ID 不同。
- **未驗證、要先做 spike 的事**（ADR-0003 §2.1 已經列為 spike）：
  - 沒有螢幕時怎麼跑 Chromium（rpi4 套件靠桌面工作階段自動啟動；無螢幕要虛擬顯示或 headless，headless 模式下取得麥克風與自動播放是否正常**不知道**）。
  - Pi 4（2 GB）同時跑 Chromium、duckd、之後的導航，CPU 與記憶體夠不夠。
  - 回音消除：一般 USB 麥克風沒有硬體 AEC，只能靠 Chromium 的 `echoCancellation`；喇叭和麥克風都在鴨子身上、距離很近，效果要實測。
  - 舵機噪音下的收音品質。
  - 輸出裝置偏好是全域一份（事實 4）：Mac 上選的裝置 ID 在 Pi 上不存在。rpi4 終端現在怎麼處理這件事沒有查清楚，要在 spike 確認。
- 這個作法裡 `presence` 的來源就在鴨子自己的 Pi 上（頁面知道完整的聽／想／說），但頁面的 CSP 是 `connect-src 'self'`（`server/page-headers.ts:11`），**不能直接連 duckd**；還是要經核心（批次 D4b：頁面回報 phase → 核心 → hub → 鴨子）。

## 3. 麥克風陣列接上後（ADR-0005：標準版 reSpeaker XVF3800，裝在頭上）

路線 A 不變，換掉收音與播放的硬體：

| 項目 | 變化 | 在哪裡做 |
|---|---|---|
| 收音 | 換成麥克風陣列，硬體做回音消除、波束成形、降噪 | 鴨子（硬體＋系統音訊層） |
| 播放 | 喇叭改由陣列的輸出驅動，讓回音消除的參考訊號就是實際播出的聲音（ADR-0010 §4）；陣列是否用自己的播放訊號當參考**要到貨驗證** | 鴨子 |
| 聲源方向（DOA） | 從陣列的 USB 控制介面讀，**不經過頁面**。頁面的收音在聲道數不是 1、2、4、6 時只留第 1 聲道（`spike/wake/direction/logic.ts:31-35`），所以頁面拿不到方向，也不該靠它 | 鴨子（`robot/audio/`），結果以 duck-link 事件 `wake_word` 的 `data` 回報 |
| 喚醒詞 | 鴨子的喚醒詞預設是「Hey 鴨子」、可以改（ADR-0003 §3，2026-11-26 決定）。兩個作法：(a) 沿用頁面的喚醒（Pi 上的 Chromium 自己偵測；AIOS 現在的關鍵詞只有「Hello Nous」「Hey Nous」，要加「Hey 鴨子」得改 AIOS 的喚醒設定）；(b) 鴨子本機原生偵測（`robot/audio/`） | (a) 不用改 AIOS；(b) 偵測在鴨子，但「叫醒後開始一通對話」要 AIOS 配合（見 §4） |
| 多裝置仲裁 | Mac、rpi4、鴨子同時聽到同一句話只回應一次 | AIOS（批次 D6） |
| 找人 | 喚醒 → DOA → 轉身 → 找臉（ADR-0003 §4） | 鴨子本機；Nous 只下 `find_person` |

AIOS 的喚醒方向 spike（`spike/wake/direction/`）量的是不同角度的喚醒成功率，**不是**聲源方向估計；AIOS 沒有 DOA 的程式可以重用。DOA 的讀法 ADR-0003 §4 指定沿用 FamilyRecorder。

## 4. 哪些要 AIOS 改、哪些在鴨子端做

| 能力 | 鴨子端（本 repo，`robot/`） | Nous 端（本 repo，`nous_adapter/`，之後搬進 AIOS） | AIOS 核心／頁面要新增的 |
|---|---|---|---|
| Nous 用語音叫鴨子做動作 | duckd 執行並回報 | DuckAdapter、hub（**已完成，對 mock 測過**） | D1、D2 |
| 鴨子跟著對話狀態做動作 | `presence` 編排 | PresenceDriver（**已完成，對 mock 測過**） | D4a（粗略）、D4b（準確） |
| Nous 的聲音從鴨子出來 | 終端套件、音訊輸出鏈、變聲 | — | 最少不用改（路線 A）；輸出裝置偏好可能要分終端 |
| 鴨子聽人說話 | 麥克風、回音消除 | — | 同上 |
| 說話時跟著音量動 | **建議在鴨子上量自己正在播的聲音**（音訊層的監聽），不經網路 | `presence` 只送狀態 | 不用（若採這個建議）。否則要頁面回報音量 |
| 鴨子自己的喚醒詞 | 本機偵測（原生）或頁面偵測 | DuckTerminal 轉 `wake_word` 事件（入口已有） | D6：喚醒關鍵詞依終端設定、仲裁；核心收到鴨子的喚醒事件後怎麼開始一通屬於鴨子頁面的對話——**現況沒有這條路** |
| Nous 透過鴨子主動開口 | 播放 | — | D7：把對話指定到某台終端，**可行性未查證** |
| 變聲、本機音效、隱私與音量閘門 | 全部在鴨子（ADR-0010 §3、§6、§7） | — | 不用 |
| 連不上 Nous 時的聲音 | 預錄提示（ADR-0010 §6） | — | 不用 |

## 5. 建議的順序

1. **作法 0**：AIOS 批次 D1、D2、D4a。用現在的硬體就能看到「跟 Nous 對話時鴨子有反應、能叫它轉頭點頭」。
2. **路線 A 的 spike**（不用等麥克風陣列）：在鴨子的 Pi 4 上，接一支 USB 麥克風，無螢幕跑 Nous 頁面，量 CPU、記憶體、延遲、回音。這是 ADR-0003 §2.1 本來就要做的 spike；結果決定走路線 A 還是 B。**要有人在場，而且會出聲**，不能在夜間做。
3. spike 通過 → 鴨子的終端套件、AIOS 批次 D4b（準確的 `presence`）。
4. 麥克風陣列到貨 → 換收音與播放、DOA、鴨子自己的喚醒詞（D6）。
5. D7（指定終端、主動開口）最後，等前面的使用經驗再決定要不要做。

spike 不通過（Pi 4 跑不動 Chromium，或無螢幕拿不到麥克風）的退路是路線 B，代價是 AIOS 核心要新增音訊收送，工作量大，要另寫 ADR。

## 6. 需要使用者決定或在場的事

- 要不要先接一支 USB 麥克風做路線 A 的 spike（建議要）；用哪一支。
- 試聽與音量（會出聲，白天、有人在場）。
- 鴨子的終端 ID（喚醒詞已定：預設「Hey 鴨子」，ADR-0003 §3）。
- 作法 1（把 Mac 的聲音轉送到鴨子）要不要花時間試。
